# قواعد بنية ملفات الكود

هذه القواعد هي خط الأساس لإعادة تنظيم المشروع. يبدأ نطاقها بملفات الإنتاج تحت
`app/`. ستبقى ملفات الاختبارات وأدوات التطوير خارج قاعدة «صنف واحد لكل ملف» في
المرحلة الأولى لأنها قد تحتوي أصنافاً مساعدة خاصة بالاختبار أو التشغيل.

## خط الأساس الحالي

تم تسجيل القياس التالي في 2026-08-18 قبل بدء الفصل:

| المؤشر | القيمة |
| --- | ---: |
| ملفات Python المفحوصة | 220 |
| الأصناف العلوية | 398 |
| ملفات متعددة الأصناف | 71 |
| ملفات تتجاوز 350 سطراً | 32 |
| أخطاء parsing | 0 |

بعد فصل `core/contracts` وتجميع الملفات داخل حزم فرعية أصبحت الحزمة تحتوي 108
ملفات Python و18 حزمة مجال و85 صنفاً، مع صفر مخالفات بنيوية. وعلى مستوى `app/`
انخفضت المخالفات من 103 إلى 85.

تم أيضاً تجميع الاستثناءات والسياسات متعددة الأصناف داخل حزمها الخاصة تحت
`app/core/exceptions/` و`app/core/policies/`، مع إبقاء واجهات الاستيراد القديمة
متاحة عبر `__init__.py`. بعد هذه المرحلة انخفض إجمالي مخالفات `app/` إلى 80،
وأصبحت حزم الاستثناءات والسياسات المفككة بلا مخالفات بنيوية.

في الخطوة التالية جُمعت وحدات `app/capabilities/investigation/` متعددة الأصناف
داخل حزم مجالية، مع الحفاظ على مسارات الاستيراد السابقة. أصبحت هذه الحزمة تضم
78 ملف Python بلا أي ملف متعدد الأصناف. كما فُصلت خدمة لقطة التشغيل إلى خدمة
الدمج، والمُسلسل، ومحوّل القيم الآمنة بصيغة JSON، وفُصل إنشاء عميل السرد النهائي
عن خدمته. كما فُصلت حلقة التحقيق إلى تنفيذ الأدوات والجولات وإنهاء النتيجة،
ولم يعد داخل هذه الحزمة ملف يتجاوز 350 سطراً. يعرض الفحص الحالي للتطبيق
403 ملفاً، و41 ملفاً متعدد الأصناف، و22 ملفاً يتجاوز 350 سطراً، وصفر أخطاء
parsing. وبدأت المرحلة التالية بتجميع `full_text_retriever` داخل حزمة تضم
المرشح، وباني الاستعلام، والمنفّذ، فأصبح القياس الحالي 406 ملفات و40 ملفاً
متعدد الأصناف، مع بقاء 22 ملفاً كبيراً وصفر أخطاء parsing.

ثم جُمعت مكونات `hybrid_retriever` و`reuse_policy` و`structured_compatibility`
بالطريقة نفسها، وأصبح القياس الحالي للتطبيق 414 ملفاً، و37 ملفاً متعدد
الأصناف، و21 ملفاً يتجاوز 350 سطراً، مع صفر أخطاء parsing.

وفُصل `analysis_orchestrator` إلى منسق رئيسي، ومعالج لإعادة الاستخدام المطابق،
ومكوّن لحفظ وفهرسة التحليل الجديد. أصبح القياس الحالي 417 ملفاً، و37 ملفاً
متعدد الأصناف، و20 ملفاً يتجاوز 350 سطراً، مع صفر أخطاء parsing.

ثم أُعيد تنظيم وحدات المعرفة السبع (`chunker` و`indexer` و`ingestion_contracts`
و`parsers` و`retrieval` و`source_loader` و`source_registry`) داخل حزم مستقلة،
وأصبح القياس الحالي 438 ملفاً، و30 ملفاً متعدد الأصناف، و19 ملفاً يتجاوز 350
سطراً، مع صفر أخطاء parsing.

وأُعيد تنظيم مكونات `capabilities/monitoring` إلى حزمتَي `scheduler` و`service`
مع فصل العقود والبروتوكولات عن التنفيذ. أصبح القياس الحالي 448 ملفاً، و28
ملفاً متعدد الأصناف، و18 ملفاً يتجاوز 350 سطراً، مع صفر أخطاء parsing.

ثم أُعيد تنظيم `capabilities/remediation` إلى حزم `execution` و
`autonomous_execution_service` و`service`. فُصلت خدمة المعالجة إلى مكونات
التخطيط، والتحقق المعزول، والموافقة، والتنفيذ، والاستعلام، والدعم، مع إبقاء
واجهات الاستيراد العامة. أصبح القياس الحالي للتطبيق 472 ملفاً، و27 ملفاً
متعدد الأصناف، و16 ملفاً يتجاوز 350 سطراً، مع صفر أخطاء parsing. أما حزمة
المعالجة نفسها فأصبحت بلا مخالفات بنيوية.

ثم فُصلت نماذج قاعدة البيانات متعددة الأصناف إلى حزم مستقلة، بما فيها نماذج
المعالجة الذاتية، كما فُصلت نتيجة بحث المعرفة ومكونات اتصال SSH. أصبح القياس
الحالي للتطبيق 504 ملفات، و18 ملفاً متعدد الأصناف، و15 ملفاً يتجاوز 350 سطراً،
مع صفر أخطاء parsing. وأصبحت حزم النماذج وملفات SSH والبحث المفصولة بلا
مخالفات بنيوية.

واكتملت بعد ذلك إعادة هيكلة المستودعات الكبيرة إلى مكونات عمليات داخل حزمها،
مع الحفاظ على واجهات المستودعات العامة. أصبح القياس الحالي للتطبيق 525 ملفاً،
و18 ملفاً متعدد الأصناف، و9 ملفات تتجاوز 350 سطراً، مع صفر أخطاء parsing. أما
طبقة `app/infrastructure` فأصبحت بلا مخالفات بنيوية.

ثم أُعيد تنظيم واجهات الإدارة إلى حزم مخططات، ومكونات مصادقة، ومسارات API
مجزأة، كما أُعيد تنظيم `runtime/claude` إلى نماذج واستثناءات وأوامر ومشغلات
ومكونات مراقبة صغيرة. أصبح القياس الحالي للتطبيق 608 ملفات، وملفان متعددَا
الأصناف، و4 ملفات تتجاوز 350 سطراً، مع صفر أخطاء parsing. وأصبحت طبقتا
واجهات الإدارة وruntime/claude بلا مخالفات بنيوية.

وأخيراً فُصلت مكونات التركيب وواجهات MCP وعميل Ollama، وخُفّض ملف الإعدادات
إلى الحد التشغيلي. أصبح القياس النهائي الحالي للتطبيق 515 ملفاً، ويضم 449
صنفاً علوياً، بصفر ملفات متعددة الأصناف، وصفر ملفات تتجاوز 350 سطراً، وصفر
أخطاء parsing. وبذلك تمر
بوابة البنية كاملة عند تشغيل:

```powershell
python tools/dev/structure_audit.py --root app --strict
```

## القواعد

1. يحتوي كل ملف Python على صنف علوي واحد كحد أقصى.
2. يشمل الصنف كل `class` و`Enum` و`dataclass` و`Protocol` وORM model.
3. يمكن لملف الواجهة أو إعادة التصدير أن يحتوي صفراً من الأصناف، ويجب أن يبقى
   خفيفاً ولا يضيف منطقاً تنفيذياً.
4. الهدف التشغيلي للملف هو ألا يتجاوز 350 سطراً. الملف الأكبر يحتاج إلى
   تفكيك إضافي أو استثناء موثق بسبب طبيعة تقنية واضحة.
5. لا يجمع الملف الواحد بين عقد المجال، وبروتوكولات البنية التحتية، وتنفيذ
   الخدمة، وطبقة HTTP.
6. تكون ملفات `__init__.py` محصورة في الحزم الرئيسية تحت `app/` فقط:
   `app/` و`capabilities/` و`composition/` و`core/` و`infrastructure/`
   و`interfaces/` و`runtime/`.
7. الحزم الداخلية تعمل كـ Namespace Packages، لذلك تستورد الرموز من ملفاتها
   الأصلية مباشرة، ولا تعتمد على إعادة تصدير من `__init__.py`.
8. تُجمع العقود داخل حزم فرعية حسب المجال، مثل `contracts/analysis/` و
   `contracts/investigation/`، مع استخدام مسار الوحدة الأصلية عند الاستيراد.

## الفحص

الفاحص الموجود في `tools/dev/structure_audit.py` يعمل دون استيراد التطبيق:

```powershell
python tools/dev/structure_audit.py --root app
```

وعند اكتمال إعادة التنظيم يمكن تفعيل بوابة الفشل:

```powershell
python tools/dev/structure_audit.py --root app --strict
```

لا نستخدم `--strict` في بداية الترحيل، لأن المخالفات الحالية هي baseline العمل
الذي ستزيله المراحل التالية.
